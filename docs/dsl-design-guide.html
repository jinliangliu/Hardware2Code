Hardware2Code DSL 设计指南

从硬件描述到业务逻辑——嵌入式状态机 DSL 完全参考

一、项目概述

Hardware2Code 是一个面向 STM32 微控制器的模型驱动代码生成工具。它以 YAML 硬件描述文件 为核心，自动生成包含 FreeRTOS、HAL 层及业务逻辑的完整工程。业务逻辑 DSL 是其中的核心创新，让开发者通过声明式语法定义复杂的状态机、事件驱动行为和定时动作，而无需手写 C 代码。

二、DSL 设计哲学

  • 声明式描述：用 YAML 表达“做什么”，而非“怎么做”。
  • 事件驱动：所有行为通过事件触发，事件管理集中化。
  • 层次化状态机：支持单区域、多区域并行以及嵌套复合状态，鼓励模块化设计。
  • 动作库丰富：内置翻转 LED、启动定时器、数学计算、条件执行、事件发布、时间线等常用动作，可组合使用。
  • 可测试性：生成的状态机代码与硬件解耦，配套 Unity 单元测试可直接在 PC 运行。
  • 低功耗感知：业务逻辑与 RTC 唤醒深度集成，空闲时自动进入 STOP 模式。

三、核心语法参考

3.1 基本结构

在 YAML 中通过 business_flow 节点定义业务逻辑。支持两种模式：单区域顺序状态机 和 多区域并行状态机。

单区域模式

business_flow:
  initial_state: "IDLE"
  states:
    - name: "IDLE"
      transitions:
        - event: "BUTTON_PRESS"
          target: "ACTIVE"
          actions:
            - "toggle_led"
    - name: "ACTIVE"
      transitions:
        - event: "RTC_TICK"
          target: "IDLE"

多区域并行模式

business_flow:
  regions:
    - name: "button_control"
      initial_state: "UP"
      states: ...
    - name: "led_control"
      initial_state: "OFF"
      states: ...

3.2 状态

每个状态可包含以下属性：

  • name 状态名，必需。
  • transitions 转换列表。
  • on_entry / on_exit 进入/退出时执行的动作列表。
  • after 超时毫秒数，到期自动产生 EVENT_TIMER_EXPIRED_<state>_timeout 事件。
  • history 布尔值，为 true 时启用历史状态记忆。
  • states 嵌套子状态定义，形成复合状态。

3.3 转换

transitions:
  - event: "BUTTON_PRESS"        # 必需，事件名（前缀 EVENT_ 自动补全）
    target: "ACTIVE"              # 目标状态名
    guard: "press_count < 3"     # 可选，C 语言条件表达式
    actions:                     # 可选，触发时执行的动作

3.4 动作库

动作语法说明示例
toggle_led翻转 LED（需存在 LED 引脚和 led_task）toggle_led
start_timer <name> <ms>创建一次性定时器，到期产生 EVENT_TIMER_EXPIRED_<name>start_timer exit_timer 3000
stop_timer <name>停止指定定时器stop_timer exit_timer
set <var> <value|inc|dec>变量赋值、自增或自减set press_count inc
calc <var> = <expr>数学表达式赋值（C 语法）calc press_count = press_count * 2 + 1
publish <event>同步发布事件（立即递归调用状态机）publish EMERGENCY
publish_async <event>异步发布事件（放入全局事件队列）publish_async LED_ON
defer <ms> => <action>延迟执行一个子动作defer 5000 => toggle_led
when <condition> => <action>条件执行子动作when press_count < 3 => toggle_led
send_to <region> <event>向并行区域发送事件（实际为 publish_async）send_to led_region LED_ON
timeline: <ms1>=><action1>, <ms2>=><action2>, ...按时间序列执行多个延迟动作timeline: 1000=>toggle_led, 2000=>publish TIMEOUT

3.5 变量

变量在 variables 列表中声明，类型直接使用 C 标准类型（如 uint32_t）。并行模式下变量自动添加区域前缀以避免冲突。

variables:
  - name: "press_count"
    type: "uint32_t"
    initial: 0

3.6 事件

事件分为预定义事件和动态事件。预定义事件包括：

  • EVENT_BUTTON_PRESS、EVENT_RTC_TICK、EVENT_MINUTE_TICK 等
  • EVENT_RETURN（子状态返回专用）

动态事件由 start_timer、after、publish/publish_async 自动注册，无需手动声明。

四、高级特性

4.1 嵌套引用与变量作用域

通过 type: "ref" 和 ref 字段，可引用外部 YAML 文件中定义的业务流，实现模块化复用。使用 namespace 字段可为被引用流的所有变量和内部状态添加前缀，避免名称冲突。

states:
  - name: "DEEP"
    type: "ref"
    ref: "common_subflow.yaml"
    namespace: "sub"    # 内部变量 local_counter 将变为 sub_local_counter

被引用的子状态机可以继续嵌套引用，形成多层结构。

4.2 时间线动作

timeline 允许在进入状态时启动一系列延迟动作，常用于实现复杂的异步操作序列。

on_entry:
  - "timeline: 1000=>toggle_led, 3000=>toggle_led, 5000=>publish_async TIMEOUT"

该动作会自动创建多个 RTC 定时器，并生成对应的回调函数，模板无需修改。

4.3 并行区域通信

并行区域（regions）通过全局事件队列进行通信。使用 send_to 或 publish_async 将事件放入队列，目标区域监听对应事件即可响应。

actions:
  - "send_to led_region LED_ON"   # 发送事件到 led_region

4.4 历史状态

为复合状态设置 history: true，离开后再进入时会恢复到上一次的子状态，而不是从初始子状态开始。

五、并行区域设计规范

当业务需要多个独立模块并发工作时，使用 regions 定义并行区域。每个区域拥有自己的状态、变量和转换，通过全局事件队列通信。

5.1 区域划分原则

  • 功能解耦：按硬件外设或业务功能划分（如“按键处理”、“LED 控制”、“传感器读取”）。
  • 独立状态：每个区域有独立的状态变量，互不干扰。
  • 事件通信：使用 send_to 或 publish_async 发送自定义事件，通过事件队列传递给目标区域。

5.2 事件命名指南

  • 使用 UPPER_SNAKE_CASE：如 LED_ON、MOTOR_START。
  • 添加区域前缀避免冲突：例如 BUTTON_LED_ON 而非直接 LED_ON。
  • 事件名与动作中的引用完全一致（空格替换为下划线）。
  • 预定义事件保留关键字：不要重新定义 RTC_TICK、BUTTON_PRESS 等硬件事件。
